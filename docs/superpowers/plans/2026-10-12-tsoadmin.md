# tsoadmin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native execution or superpowers:subagent-driven-development if the user chooses delegation. Track steps using checkboxes.

**Goal:** Deliver a runnable TypeScript starter with REST CRUD and authenticated administration of the same PostgreSQL records.

**Architecture:** Express mounts tsoa-generated API routes, Swagger UI, and AdminJS. Prisma supplies database access and migrations; PostgreSQL also stores admin sessions.

**Tech Stack:** Node.js, TypeScript ESM, Express, tsoa, Prisma, PostgreSQL, AdminJS, Vitest, Supertest.

**Spec:** `../../design.md`

## Global Constraints

- Project folder: `tsoadmin`; synced `sources/` files remain read-only.
- Use ESM and select mutually compatible dependency versions before installation.
- Admin access requires environment-configured credentials and persistent PostgreSQL-backed sessions; no working default credentials.
- Fail startup if required secrets are missing.
- Session cookies are HTTP-only and secure in production; proxy trust is explicit.
- Public frontend and deployment are outside initial scope. Sample CRUD API is for local development.
- Admin writes bypass API services: database constraints enforce shared invariants.

## Review Focus

1. Negative or fractional prices must fail, including writes through AdminJS.
2. Missing or malformed environment settings must fail without printing secrets.
3. Unknown IDs and malformed JSON must return useful errors without stack traces.
4. Failed admin login and unauthenticated resource requests must not expose records.
5. Tests must use a separate database and never reset the development database.

## File responsibilities

`package.json`, `tsconfig.json`, `tsoa.json`, `vitest.config.ts`: build and test configuration.
`compose.yaml`, `.env.example`, `.gitignore`: local database and configuration guidance.
`prisma/schema.prisma`, `prisma/migrations/`, `prisma/seed.ts`: schema, constraints, example data.
`src/config.ts`, `src/db.ts`: validated configuration and shared Prisma client.
`src/products/service.ts`, `src/products/controller.ts`: persistence and REST contract.
`src/admin.ts`: AdminJS resource, credential verification, session store.
`src/app.ts`, `src/server.ts`, `src/errors.ts`: application composition, startup/shutdown, error translation.
`src/generated/`: generated routes and OpenAPI; generated during builds.
`tests/config.test.ts`, `tests/api.test.ts`, `tests/admin.test.ts`, `tests/setup.ts`: acceptance checks and isolated database setup.
`README.md`: setup, limitations, extension instructions.

### Task 1: Database and runnable foundation

**Produces:** `config` with database URL, admin email/password, session secret, port, environment, and proxy settings; shared `prisma`; `Product` model.

- [ ] Check installed Node/package-manager/Docker capabilities and package registry peer constraints. Pin compatible releases and commit the dependency lockfile. Prefer Express 4 and the Prisma major explicitly supported by the AdminJS adapter; do not assume latest releases interoperate.
- [ ] Add configuration tests for absent secrets, invalid port, short session secret, and valid settings. Run them first and confirm failures are attributable to the missing implementation.
- [ ] Implement validated environment loading with no secret values in errors. Configure strict TypeScript with ESM, decorator support, and tsoa route generation.
- [ ] Create a PostgreSQL Compose service bound to localhost. Define this Prisma model:

```prisma
model Product {
  id           Int      @id @default(autoincrement())
  name         String
  priceInCents Int
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

- [ ] Generate the initial migration and append database checks for `priceInCents >= 0` and a nonblank trimmed name. PostgreSQL integer storage prevents fractional prices. Add idempotent seed data keyed by a fixed example ID.
- [ ] Set up test database configuration requiring a database name ending in `_test`, distinct from the development URL, before migrations or cleanup. Test rejection of unsafe URLs.
- [ ] Run config tests, Prisma generation, and schema validation. Record results and commit only project files if Git is initialized.

### Task 2: REST API and documentation

**Consumes:** shared `prisma`. **Produces:** `createApp(): Promise<Express>`, generated `/api/products` CRUD routes, `/health`, `/docs`, and `/openapi.json`.

- [ ] Write database-backed Supertest acceptance cases before implementing controllers:

```ts
const created = await request(app)
  .post('/api/products')
  .send({ name: 'Bread', priceInCents: 250 })
  .expect(201);
await request(app).get(`/api/products/${created.body.id}`).expect(200);
await request(app)
  .patch(`/api/products/${created.body.id}`)
  .send({ priceInCents: 300 })
  .expect(200);
await request(app).get('/api/products').expect(200);
await request(app).delete(`/api/products/${created.body.id}`).expect(204);
await request(app).get(`/api/products/${created.body.id}`).expect(404);
await request(app).post('/api/products').send({ name: 'Bread', priceInCents: -1 }).expect(400);
await request(app).post('/api/products').send({ name: 'Bread', priceInCents: 1.5 }).expect(400);
```

- [ ] Add cases for whitespace-only name, empty update, extra properties, invalid ID, malformed JSON, and a generic unexpected 500 response with no stack trace. Run tests and confirm they fail before implementation.
- [ ] Implement service methods `list`, `get`, `create`, `update`, `remove`. Convert missing Prisma records to 404; database constraint failures to 400. Keep other internal errors private.
- [ ] Implement tsoa DTOs and controller methods. Use integer/minimum annotations for price and ID, reject extra properties in tsoa configuration, and explicit service validation for blank names and empty patches.
- [ ] Mount generated routes after bounded JSON parsing, followed by error handling. Provide health and documentation endpoints; generate OpenAPI as part of development and production scripts.
- [ ] Assert OpenAPI contains all CRUD paths, invalid bodies fail before persistence, and Swagger UI responds. Run API tests and build; commit verified changes if Git is initialized.

### Task 3: Authenticated administration

**Consumes:** `config`, `prisma`, `Product` model. **Produces:** AdminJS router at `/admin` attached inside `createApp()`.

- [ ] Write tests that anonymous `/admin` and Product action requests require login, bad credentials fail, and valid login retains a session. Run first to establish failures.
- [ ] Register `@adminjs/prisma` with `getModelByName('Product')` and the shared Prisma client. Mark generated IDs/timestamps noneditable. Mount the AdminJS router before any parser that conflicts with its multipart handling.
- [ ] Build the authenticated Express router with environment credentials, constant-time digest comparison, and `connect-pg-simple`. Use a distinct session table, `resave: false`, `saveUninitialized: false`, HTTP-only cookies, production secure cookies, and explicit proxy trust.
- [ ] Prepare AdminJS assets for both development and production; await initialization before serving requests.
- [ ] Exercise authenticated list, create, edit, and delete through admin action endpoints. Confirm API reads the same records. Test negative admin prices fail database constraints and failed login never creates an authenticated session.
- [ ] Test secure-cookie configuration and verify session persistence using the PostgreSQL session table. Run admin and API tests together and commit verified changes if Git is initialized.

### Task 4: Complete starter and acceptance verification

**Consumes:** runnable application. **Produces:** reproducible setup instructions and final validation report.

- [ ] Add server startup bound to localhost by default, database connection verification, and graceful shutdown closing HTTP, session-pool, and Prisma connections.
- [ ] Document the exact commands for installing, copying `.env.example`, setting credentials, starting PostgreSQL, applying migrations, seeding, running development, and opening `/docs` and `/admin`. Include test-database setup and production build/start commands.
- [ ] Explain the unauthenticated sample API, shared database constraints, admin customization, and pinned compatibility decisions. Ignore `.env`, dependencies, generated build output, and admin asset caches.
- [ ] Execute `npm run typecheck`, `npm run build`, and `npm test` against the isolated test database. Smoke-test production startup, health, docs, and authenticated admin. Fix any failures and rerun affected checks.
- [ ] Review all files for accidental secrets, placeholders, and missing scripts. Report changes, compatibility caveats, and actual test results; explicitly identify any database or runtime checks that could not run.

## Execution choice

Native execution is recommended because these four tasks share a small application and tightly connected interfaces. Delegated execution is available if the user prefers independent task reviews.
